# ClawBoard 架构重构 · 增量 PRD

> 文档性质：**增量 PRD**（只描述"本次变更部分"，不从零写 PRD）
> 产品：ClawBoard（Windows 悬浮剪贴板 & 常用语工具）
> 当前版本：v1.4.5
> 重构范围：**仅 Python 版**（C 版与 exe 行为不动）
> 优化档位：中度优化（模块化拆分 + 分层 + dataclass/类型标注 + 集中配置 + 统一状态管理）

---

## 1. 重构目标

**一句话**：在"外部行为 100% 不变、数据文件兼容、测试基线全绿"三大前提下，把 4236 行的单文件"上帝对象 + 散落模块级函数"重构成"分层 + 模块化 + 集中配置 + 统一状态管理"的可维护结构。

**成功标准（可衡量）**：

- **SC1 规模可控**：`ClawBoard.py` 主文件从 4236 行降到明显可读的规模，主类 `ClawBoard` 方法数从 97 个收敛到可读规模（具体阈值由架构师在拆分边界内定，PM 建议：主文件仅保留启动入口 + UI 编排，领域逻辑不再驻留）。
- **SC2 无散落函数**：原 60 个模块级函数（主题配色 / Win32 声明 / 剪贴板读写 / 敏感识别 / 时间格式化 / 来源采集 / 内容分类 / 数据迁移 / 图标生成 / 开机自启 / 文本变换入口等）全部归位到职责明确的模块，主文件不再含领域函数定义。
- **SC3 无魔法值**：`DEFAULT_SETTINGS` 之外的 163 个模块级常量 / 赋值语句收敛到集中配置单一来源，业务模块内不再出现裸魔法常量。
- **SC4 测试全绿**：现有测试基线全部通过（`test_core.py` 27 项 + `_t14.py` 38 项 + `_t22.py` 26 项 + `_t24.py` 24 项 = **115 项**）。
- **SC5 数据互通**：`ClawBoard数据.json` 格式不变，老数据直接读、新数据老版本可读、C 版仍能读同一份数据文件（两版互通）。

## 2. 痛点清单（现状为什么难维护）

1. **单文件超大、职责混乱**：`ClawBoard.py` 单文件 4236 行，主类 `ClawBoard` 有 97 个方法，另有 60 个模块级函数散落在文件里——主题配色、Win32 声明、剪贴板读写、敏感识别、时间格式化、来源采集、内容分类、数据迁移、图标生成、开机自启、文本变换入口……全挤在一起。项目已有模块化苗头（`query.py` 216 行、`transform.py` 236 行），但主文件始终没动。

2. **反复出编辑事故**：用 Edit 删除/修改方法时，`old_string` 跨方法边界，导致重复方法定义、语法错误（历史记录多次出现）。单文件 + 大方法是这类事故的直接温床。

3. **状态字段散落、隐式初始化**：`_restore` 只在折叠分支里赋值、`rec` 只在新条目分支里赋值，分别在 v1.4.5 hotfix 里暴露为两个**真崩溃**。97 个方法里没人能一眼看出哪个状态在哪儿初始化。

4. **四个跨版本反复踩的坑，全靠人记**：
   - pack 空间分配/顺序（固定尺寸控件必须先于带 expand 的控件 pack）
   - Tk 事件不冒泡（滚轮/双击必须绑到每个子控件）
   - DPI 未声明导致测量失真（读窗口坐标前必须 `SetProcessDpiAwareness(2)`）
   - 压测/自测路径隐式写盘（模块级 `NO_SAVE` 守卫）

5. **配置散落、魔法值遍地**：`DEFAULT_SETTINGS` 一个 dict + 163 个模块级常量/赋值语句，改一处要人肉找全所有引用点。

## 3. 需求池

### P0（必须做，不做这次重构没意义）

#### R1 · 模块化拆分主文件
- **要什么**：把 `ClawBoard.py` 里 97 个方法 + 60 个模块级函数按领域拆分，主文件瘦身为"启动入口 + UI 编排"，领域逻辑（剪贴板读写 / Win32 与 DPI 声明 / 主题配色 / 敏感识别 / 时间格式化 / 来源采集 / 内容分类 / 数据迁移 / 图标生成 / 开机自启 / 文本变换入口等）归入独立模块；已独立的 `query.py`、`transform.py` 一并纳入统一结构，不被破坏。
- **为什么**：单文件 4236 行 + 97 方法是编辑事故（痛点 2）与状态散落（痛点 3）的根因。
- **验收标准**：
  - 主文件不再包含上述领域函数/方法的定义，只保留编排与入口职责；
  - 拆分后应用可正常启动，全部交互可用（见 NFR1）；
  - `query.py`、`transform.py` 功能不回归，27 项文本变换、搜索语法解析行为不变。

#### R2 · 集中配置
- **要什么**：把 `DEFAULT_SETTINGS` 与 163 个模块级常量/赋值收敛到一个**配置单一来源**，替换散落的魔法常量；配置项命名与含义保持清晰。
- **为什么**：魔法值遍地、改一处要全量检索（痛点 5）。
- **验收标准**：
  - 业务模块内不再出现裸魔法常量，全部引用集中配置；
  - 配置的默认值与 v1.4.5 行为完全一致（`ClawBoard数据.json` 里已有字段不受影响）。

#### R3 · 统一状态管理
- **要什么**：把散落在不同分支里隐式初始化的运行时状态字段（如 `_restore`、`rec`）集中到明确的初始化处，保证所有状态字段在构造/初始化阶段就有默认值。
- **为什么**：状态隐式初始化已在 v1.4.5 hotfix 暴露两个真崩溃（痛点 3）。
- **验收标准**：
  - 所有运行时状态字段有明确、唯一的初始化位置，无"只在某分支赋值"的隐式初始化；
  - 折叠/贴边、新条目新增、剪贴板采集等场景回归不崩溃（以 `crash.log` 中历史崩溃场景复测通过为准）。

#### R4 · 类型化数据结构
- **要什么**：用 dataclass + 类型标注替换散落的 dict 与魔法结构，至少覆盖配置结构、条目/剪贴板数据、运行时状态等核心数据结构；只使用标准库（`dataclasses` / `typing` / `enum`）。
- **为什么**：dict 无结构约束，字段散落易写错、难以静态发现错误，与 R2/R3 互相强化。
- **验收标准**：
  - 核心数据结构有明确类型，IDE 可静态检查；
  - 序列化/反序列化结果与现有 `ClawBoard数据.json` 完全兼容（见 NFR2）；
  - 不引入任何第三方依赖。

#### R5 · 打包链路同步更新
- **要什么**：模块拆分后，同步更新 PyInstaller spec（入口仍为 `ClawBoard.py`，新增模块与既有 `query`/`transform` 一并列为 hiddenimports），保证打包继续可用。
- **为什么**：拆分后若 spec 不更新，打包产物会缺失新模块、运行时报 ImportError。
- **验收标准**：
  - `ClawBoard.spec` 构建出可运行的 exe，启动后功能完整；
  - 打包后不出现因拆分导致的模块缺失/导入失败。

## 5. 明确的边界（本次不做什么）

- **不动 C 版**：`ClawBoardC` 及 C 版产物本次零改动。
- **不引入第三方依赖**：保持零依赖，不做任何 pip 依赖。
- **不改存储方案**：不改成 SQLite / 数据库，继续用 JSON 单文件。
- **不重写 UI / 不改交互**：UI 布局、快捷键、折叠/贴边/热键/托盘等交互一律不变。
- **不改数据格式**：`ClawBoard数据.json` 字段与结构不变。
- **不做功能新增**：本次为纯架构重构 + 中度优化，不新增任何面向用户的功能（除非另行立项）。
- **不写架构设计/代码**：本 PRD 只定义"要什么/为什么/验收标准"，具体模块划分、类与函数设计、实现代码由架构师与工程师负责。
